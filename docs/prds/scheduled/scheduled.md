# 定时任务优化需求（PRD）

## 写在前面

### 这份文档要回答什么

把 6 条用户反馈,整理成可开发、可验收的定时任务优化需求。既包含 bug 修复,也包含体验优化。

### 名词约定

- **定时任务**:用户设定"在某个时间 / 按某个频率,自动让某个助手执行一段指令"的任务。
- **任务会话**:定时任务每次执行,都会产生或延用一个对话(会话)。一个定时任务名下可能挂着多个任务会话。
- **对话内创建**:用户不点表单,而是在和助手聊天时用自然语言说"每天 9 点帮我做 X",让系统自动建一个定时任务。
- **手动创建**:用户点击界面上的"新建定时任务"按钮,填表单创建。
- **聚合页**:顶部「定时任务」入口进去后的那个页面,平铺展示所有定时任务的卡片。
- **详情页**:从聚合页点进单个定时任务后的页面,展示这个任务的配置和它名下的所有任务会话。

### 编号约定

功能编号 `F-CRON-NN`:F = Feature 功能,CRON = 定时任务模块,NN = 序号。序号不代表优先级。

## 1. 创建方式改为直接调用后端接口

**功能编号**:F-CRON-01
**类型**:Bug 修复 + 重构
**实现状态**:🟡 部分完成（2.1.27）—— 界面创建入口已统一到「找管家」按钮走引导创建;但底层仍保留了旧的"解析 AI 回复文本"通道,多行指令截断的隐患未彻底根除。剩余工作:确认新入口完全不走文本解析、并移除旧解析通道。

### 想解决的问题

现在"对话内创建"定时任务时,系统是靠**读取助手回复里的一段文本**来创建任务的。助手要把任务配置写成一段带标记的文本,系统再去解析这段文本。这条链路有个硬伤:当助手把指令分成多行来写时,系统只能可靠地拿到开头部分,后面的内容会丢。

举个具体例子:用户说"每天早上帮我汇总昨天的邮件,分三点:第一点未读、第二点待回复、第三点已归档"。助手把这三点分行写进任务指令,结果创建出来的任务只带了"汇总昨天的邮件"这一句,三点要求全丢了。用户要到任务第一次跑出来、结果不对,才发现指令被截断了。

根因是:手动创建走的是一套可靠的后端接口(填什么存什么),而对话内创建绕开了这套接口,改用"解析文本"这种脆弱方式。

### 目标

对话内创建复用手动创建已经在用的那套后端接口,不再依赖解析助手回复的文本。用户在对话里说的完整指令,应当被完整、逐字地建进定时任务。

### 正常流程

1. 用户在对话里用自然语言描述一个定时任务(可以是多行、多条要求)。
2. 系统把完整的任务信息通过后端接口创建成定时任务。
3. 创建成功后,给用户一个明确的确认(任务名、执行时间、完整指令)。

### 异常情况

- 用户描述里缺少必要信息(如没说执行时间):系统应向用户追问,而不是用默认值静默创建。
- 创建接口调用失败:明确告知用户失败,不留下半成品任务。

### 验收标准

- 用户在对话里给出**多行 / 多条要求**的指令,创建出的定时任务指令内容与用户所说的一致,无截断、无丢行。
- 对话内创建与手动创建,产生的任务在字段完整度上没有差异。

## 2. 「描述」字段改为可选

**功能编号**:F-CRON-02
**类型**:优化
**实现状态**:✅ 已完成（2.1.27）—— 实际做法比"改可选"更彻底:直接把「描述」字段从创建/编辑表单移除,用户不再需要填,由系统按调度信息自动生成。这样"从没让填却被必填卡住"的问题从根上不存在了。下方原始需求保留作背景,验收以"表单无描述字段、创建/编辑均不因描述受阻"为准。

### 想解决的问题

手动创建定时任务时,"描述"字段是必填的;但对话内创建根本没有让用户填描述这一步。结果是:对话内创建出来的任务,描述天然为空。等用户之后想编辑这个任务时,编辑表单又用"描述必填"来卡他 —— 一个从没让他填过的字段,现在却不让他保存。用户被卡住,不知道该填什么。

### 目标

"描述"字段全程改为可选。无论手动创建、对话内创建,还是后续编辑,描述为空都不应阻断保存。

### 正常流程

1. 手动创建 / 编辑时,"描述"不再标记为必填,留空可直接保存。
2. 对话内创建的任务描述为空,后续编辑时可以正常保存(即使仍不填描述)。

### 异常情况

- 历史上已经存有描述的任务:编辑时原描述照常带出、可修改、也可清空。

### 验收标准

- 手动创建时描述留空,能成功保存。
- 对话内创建的任务(描述为空)进入编辑页后,不改描述也能保存成功。
- 已有描述的历史任务不受影响。

### 待讨论模块:数据库兼容性

这条涉及数据库层面的字段约束调整。当前任务表里"描述"列本身允许为空,主要是**表单校验**在强制必填,所以大概率是前端放开校验即可。但需要工程侧确认:

- 是否有其他读取路径假设了"描述一定非空"(如列表展示、搜索),放开后是否需要兜底显示。
- 历史数据中描述为空的任务是否已经存在、是否需要一次性数据订正。

**产品立场**:倾向"改为可选、不做强制数据迁移",空描述在展示处用任务名兜底。最终以工程侧兼容性评估为准。

## 3. 侧边栏定时任务分类重构

**功能编号**:F-CRON-03
**类型**:优化
**实现状态**:✅ 已完成（2.1.27）—— 已取消侧边栏的定时任务会话分类,定时任务产生的会话回归普通会话列表;顶部「定时任务」聚合入口保留。

### 想解决的问题

现在侧边栏的会话记录里,定时任务产生的会话被单独归到一个「定时任务」分类下,和普通会话隔开。这带来两个别扭:

- 定时任务产生的会话,本质上也是一次正常的对话,用户却在自己熟悉的会话列表里找不到它们。
- 侧边栏同时存在"顶部的定时任务聚合入口"和"会话列表里的定时任务分类",两处都在管定时任务,职责重叠。

### 目标

- 取消侧边栏**会话记录里**的「定时任务」分类。定时任务创建的会话,回到它们本该在的普通会话列表里(按工作目录 / 时间正常归类)。
- 保留顶部的「定时任务」聚合入口。用户要按"每个定时任务"维度查看它名下的会话时,走聚合页 → 详情页这条路径。

### 正常流程

1. 定时任务产生的会话,和普通会话一样出现在侧边栏会话列表中。
2. 用户想以"任务"为单位查看某个定时任务跑过哪些会话时,点顶部「定时任务」入口进聚合页,再点进具体任务的详情页查看。

### 异常情况

- 一个定时任务名下有多个会话:这些会话在普通列表里各自独立出现;在详情页里仍聚合在该任务名下。两处都能看到,不冲突。

### 验收标准

- 侧边栏会话列表里不再有独立的「定时任务」分类。
- 定时任务产生的会话,出现在普通会话列表中。
- 顶部「定时任务」入口 → 聚合页 → 详情页 这条查看路径保持可用。

## 4. 未读蓝点逐级冒泡

**功能编号**:F-CRON-04
**类型**:优化
**实现状态**:🟡 部分完成（2.1.27）—— 底层已能识别"某个会话有未读",但蓝点还没在侧边栏「定时任务」入口、聚合页任务卡片上显示。剩余工作是把未读态接到这几层的展示上,让蓝点真正逐级冒泡。

### 想解决的问题

定时任务在后台跑完后,对应会话上会出现一个蓝色小点表示"有新结果没看"。但这个蓝点现在只停在会话本身。用户不点进具体任务、具体会话,就感知不到"有任务跑完了"。做完 F-CRON-03 之后,侧边栏不再平铺展示每个任务会话,用户更需要一个从最外层就能看到的提醒。

### 目标

未读蓝点从最内层逐级向上冒泡,让用户在最外层的侧边栏入口就能感知"名下有任务跑完了":

```
任务会话(有新结果) → 详情页对应会话 → 聚合页对应任务卡片 → 侧边栏「定时任务」入口
```

任意一层只要下面有未读,这一层就带蓝点。

### 正常流程

1. 某个定时任务的会话跑完、产生新结果 → 该会话标记未读。
2. 未读向上冒泡:该任务在聚合页的卡片带蓝点;侧边栏顶部「定时任务」入口也带蓝点。
3. 用户点开侧边栏入口 → 看到哪个任务卡片有蓝点 → 点进详情页 → 看到哪个会话有蓝点 → 点开会话查看,该会话未读消除。
4. 当一个任务名下所有未读会话都被看过,该任务卡片的蓝点消失;当所有任务都无未读,侧边栏入口的蓝点消失。

### 异常情况

- 同一任务名下多个会话都有未读:上层蓝点表示"有 ≥1 个未读",看完其中一个、还剩其他未读时,上层蓝点仍在,直到全部看完。
- 用户当前正停留在某个会话页时,该会话跑出的新结果不应再标为未读(用户正在看)。

### 验收标准

- 任务会话产生新结果后,侧边栏「定时任务」入口出现蓝点。
- 点开并查看该会话后,若名下已无其他未读,各层蓝点随之消失。
- 名下有多个未读会话时,看完部分、上层蓝点不提前消失。

## 5. 执行时间体现在会话标题上

**功能编号**:F-CRON-05
**类型**:优化
**来源**:GitHub Issue #3465
**实现状态**:⬜ 待开发（2.1.27 未做）

### 想解决的问题

设置为"每次新建会话"模式的定时任务,跑多次后会攒下一串会话,但这些会话标题看起来几乎一样,只有任务名、没有日期。用户翻历史时无法区分"这是哪天跑的那一次",很难定位到某个具体日期的执行结果。

### 范围界定

**只针对"每次新建会话"模式**:每次执行时新建的那个会话,标题带上执行日期。

不在本需求范围内:

- "延用同一会话"模式(每次执行往同一个会话里追加)不动 —— 它不新建会话,没有"哪次执行"的区分诉求。
- 已存在会话的标题不改 —— 只在新建那一刻决定标题,不做事后回填,因此也不存在"覆盖用户自定义标题"的问题。

### 正常流程

1. "每次新建会话"模式的定时任务执行 → 新建一个会话。
2. 新建会话的标题带上执行日期,格式 `DD-MM-YY`(例如 `任务名 01-07-26`)。
3. 用户翻历史时,凭标题上的日期区分不同天的执行。

### 异常情况

- 同一天多次执行:多个会话标题的日期相同。此需求只保证"能区分到天",同一天内多次执行是否进一步区分不在本需求范围。

### 验收标准

- "每次新建会话"模式下,新建会话的标题带有该次执行的日期(`DD-MM-YY`)。
- 不同天执行产生的会话,标题日期不同、可区分。
- "延用同一会话"模式的会话标题不受影响。

## 6. 详情页会话列表支持多选删除

**功能编号**:F-CRON-06
**类型**:优化
**实现状态**:⬜ 待开发（2.1.27 未做）—— 主会话列表已有成熟的多选删除逻辑,详情页可复用。

### 想解决的问题

定时任务跑久了,名下会攒下大量会话。F-CRON-03 取消了侧边栏的定时任务会话分类(而且那个分类里本来也没有多选删除),所以用户现在没有一个顺手的地方批量清理某个任务的历史会话,只能一条一条删,很痛苦。

### 目标

在定时任务详情页的会话列表处,增加多选删除交互,让用户能一次勾选多个会话批量删除。

### 正常流程

1. 用户进入某个定时任务的详情页,看到该任务名下的会话列表。
2. 用户进入多选模式,勾选若干会话(支持全选)。
3. 用户点击删除,二次确认后批量删除选中的会话。
4. 删除后列表刷新,显示剩余会话。

### 异常情况

- 删除的会话里包含用户当前正打开的那个会话:删除后需妥善处理当前视图(如跳回详情页 / 列表)。
- 删除某个会话**不应影响定时任务本身**(与 F-CRON-07 直接相关):任务配置、下次执行都不受影响。
- 全选后删除:删空该任务名下所有会话,任务本身保留。

### 验收标准

- 详情页会话列表可进入多选模式,支持勾选、全选、批量删除,并有二次确认。
- 批量删除后,定时任务本身及其调度不受影响。

## 7. Bug:删除关联对话导致整个定时任务被删

**功能编号**:F-CRON-07
**类型**:Bug 修复
**来源**:Sentry Issue #131278645
**实现状态**:⬜ 待开发（2.1.27 未做）—— Bug 仍在:任务与对话仍强绑定,删对话仍可能连带删掉任务。注意 2.1.27 有两个名字相近的改动("让定时任务会话重新显示在历史里 + 保留助手配置"),那是另一件事,并未解决本条误删问题。

### 想解决的问题

定时任务由某条对话创建时,会记下这条对话的 id 作为"归属对话"。问题是:即使用户后来把任务切换成了别的对话(甚至换了工作目录),任务记的还是**最初那条对话的 id**。这时用户去删那条最初的旧对话,整个定时任务会跟着一起消失。

具体复现路径(来自用户上报):
1. 用户有一个定时任务,最初绑在对话 A 上。
2. 用户把任务从"延用同一对话"改成"每次新建对话",并触发了一次新建 → 产生了对话 B。
3. 用户甚至改掉了任务的工作目录。
4. 用户去删除已经用不上的旧对话 A → 整个定时任务连同它一起被删掉了。

用户的预期是:删掉一条旧对话,只删这条对话,定时任务应当还在(它现在明明关联的是新对话 / 新配置)。

### 目标

**定时任务与对话彻底解耦**:删除对话只删对话,永远不影响定时任务。任务的存续不依赖任何一条对话,包括最初创建它的那条、以及它名下最后一条对话。

### 正常流程

1. 用户删除一条与某定时任务相关的对话。
2. 只有这条对话被删除,定时任务本身保留、调度继续。
3. 即使删的是该任务名下最后一条对话,任务依然保留,进入"当前无关联对话"状态,下次执行时按其配置正常运行(需要时新建对话)。

### 异常情况

- 任务已切换到新对话 / 新工作目录后,删最初那条旧对话:任务保留。
- 一个定时任务名下有多个会话,删其中任意一个:任务保留。
- 删光名下所有对话:任务仍保留,进入"无关联对话"状态,聚合页 / 详情页正常展示该任务,不因缺对话而报错或消失。

### 验收标准

- 复现上报路径(切新对话 + 改工作目录 + 删旧对话),定时任务不消失。
- 删除任务名下任意会话(含删到一条不剩),任务保留、调度不变。
- 名下无关联对话的任务,在聚合页 / 详情页能正常展示,并能在下次执行时正常运行。

### 影响范围提醒(数据层)

彻底解耦需要放开当前"任务必须绑定一个对话 id"的数据约束(任务表 `conversation_id` 目前为必填)。这属于会碰到数据模型的改动,需工程侧处理:

- 放开约束后,历史任务数据的兼容(存量任务都带着对话 id,不需迁移,但要确保删对话时不再反向删任务)。
- "无关联对话"状态下,详情页会话列表、聚合页卡片的展示兜底。
