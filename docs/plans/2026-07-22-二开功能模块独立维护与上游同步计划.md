# 二开功能模块独立维护与上游同步实施计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在不阻塞官方 AionUi/AionCore 更新的前提下，独立维护“普通会话 → 临时 Team 连续上下文闭环”功能，并建立可重复的同步、验证、回滚和上游 PR 流程。

**Architecture:** 采用“双仓库、双主线、功能分支”的方式：两个仓库的 `main` 只跟随官方上游，功能实现保存在配套的 feature 分支；每次上游更新后，从最新上游基线创建 integration 分支，通过 cherry-pick 功能提交重新组装并验证。由于功能涉及后端数据契约、Team API、事件广播、运行时会话和前端 UI，AionUi 与 AionCore 必须作为一个版本配套单元维护，不能当作纯前端插件。

**Tech Stack:** Git（upstream/origin、feature branch、worktree、cherry-pick）、AionUi（TypeScript/React/Vitest）、AionCore（Rust/Cargo/SQLite）、WebSocket/IPC、i18n。

### 1.2 本计划覆盖的功能

- 普通会话创建临时 Team，并记录 `origin_conversation_id`。
- 创建时继承普通会话的上下文和 leader 会话关系。
- Team Agent 消息回流到来源普通会话。
- Team 创建后通过 `team.created`/`team.listChanged` 即时刷新侧边栏。
- 成员会话使用 `extra.team_id` 过滤，来源 leader 使用 `extra.teamId` 保持可见。
- 临时 Team 的状态卡、运行状态、删除后返回来源会话和视觉区分。
- AionUi/AionCore 配套测试、迁移和兼容性验证。

### 1.3 不纳入本阶段

- 不把功能重写成独立 npm/Cargo 插件。
- 不直接修改官方 `main` 后提交未经验证的混合改动。
- 不在没有上游确认的情况下宣称“等待合并”；先维护 fork，并按上游规范准备 PR。
- 不为了清理旧代码而扩大功能范围。

## 2. 分支与提交策略

### 2.1 分支命名

两个仓库使用同名、同语义分支，便于配套切换：

```text
feat/ad-hoc-team-context
integrate/ad-hoc-team-latest
```

必要时按独立主题拆分短分支：

```text
feat/aioncore-ad-hoc-team-contract
feat/aionui-ad-hoc-team-ui
```

### 2.2 提交分层

AionCore 建议按以下顺序提交：

1. `feat(team): add origin conversation contract`
2. `feat(team): promote conversation into ad-hoc team`
3. `feat(team): propagate team messages and lifecycle events`
4. `test(team): cover promotion and origin binding`

AionUi 建议按以下顺序提交：

1. `feat(conversation): add ad-hoc collaboration launcher`
2. `feat(team): show promoted conversation state`
3. `feat(conversation): sync teammate messages and runtime state`
4. `fix(team): refresh sidebar and distinguish ad-hoc teams`
5. `test(team): cover ad-hoc collaboration flows`

每个提交应能单独说明变更目的；不要把格式化、无关重命名和功能实现混在一个提交中。

## 3. 阶段计划

### Task 1：冻结当前原型并建立恢复点

**Files/Repos:** 两个仓库当前工作区；不修改业务代码。

**Step 1: 记录工作区状态**

```bash
git status --short --branch
git diff --stat
git diff --name-only
```

**Step 2: 导出补丁快照**

在各仓库使用明确文件名保存补丁（包含已跟踪和未跟踪文件清单），例如：

```bash
git diff > /tmp/aionui-ad-hoc-working.patch
git diff > /tmp/aioncore-ad-hoc-working.patch
```

未跟踪文件需单独记录，不能假设 `git diff` 会包含它们。

**Step 3: 创建功能分支并提交原型快照**

```bash
git switch -c feat/ad-hoc-team-context
git add <经过核对的功能文件>
git commit -m "feat: preserve ad-hoc team context prototype"
```

AionUi 与 AionCore 都完成后，记录两个 commit SHA 和对应关系。

**Step 4: 验证恢复能力**

```bash
git show --stat --oneline HEAD
git status --short
```

Expected：功能分支包含完整原型；工作区清洁；没有执行破坏性 reset/stash。

### Task 2：让本地 main 只跟随官方上游

**Repos:** AionUi、AionCore。

**Step 1: 获取上游引用**

```bash
git fetch upstream --prune
git branch -vv
```

**Step 2: 在功能分支上确认快照已保存**

只有在 Task 1 完成后，才允许切换到 `main`。

**Step 3: 更新 main**

```bash
git switch main
git merge --ff-only upstream/main
```

如果本地 `main` 有历史分叉，停止并人工决定是保留、归档还是建立新 worktree；不要使用 `git reset --hard`。

**Step 4: 推送到自己的 fork（可选）**

```bash
git push origin main
```

只有用户明确要求发布时才执行推送；日常同步可只保留本地 `upstream/main`。

### Task 3：建立干净的集成 worktree

**Purpose:** 避免在脏工作区中反复切换官方代码和二开代码。

**Step 1: 从最新上游创建集成分支**

```bash
git switch main
git switch -c integrate/ad-hoc-team-latest
```

更严格的做法是使用独立 worktree，目录放在仓库同级的临时目录中，避免覆盖当前开发目录。

**Step 2: 按顺序 cherry-pick AionCore 提交**

```bash
git cherry-pick <AionCore-contract-commit>
git cherry-pick <AionCore-service-commit>
git cherry-pick <AionCore-test-commit>
```

**Step 3: 按顺序 cherry-pick AionUi 提交**

```bash
git cherry-pick <AionUi-contract-commit>
git cherry-pick <AionUi-ui-commit>
git cherry-pick <AionUi-test-commit>
```

发生冲突时，优先适配官方最新接口；保留二开行为和测试，不直接覆盖上游文件。

### Task 4：核对 AionCore/AionUi 数据契约

**AionCore Files:**

- `crates/aionui-db/migrations/028_ad_hoc_team_origin_conversation.sql`
- `crates/aionui-db/src/models/team.rs`
- `crates/aionui-db/src/repository/team.rs`
- `crates/aionui-db/src/repository/sqlite_team.rs`
- `crates/aionui-team/src/types.rs`
- `crates/aionui-team/src/service.rs`
- `crates/aionui-team/src/provisioning.rs`
- `crates/aionui-team/src/routes.rs`
- `crates/aionui-api-types/src/team.rs`

**AionUi Files:**

- `packages/desktop/src/common/types/team/teamTypes.ts`
- `packages/desktop/src/common/adapter/teamMapper.ts`
- `packages/desktop/src/common/adapter/ipcBridge.ts`
- `packages/desktop/src/renderer/pages/conversation/hooks/useAdHocTeamFromConversation.ts`

**Step 1: 校验字段语义**

- `origin_conversation_id`：来源普通会话与 Team 的一对一绑定。
- `extra.teamId`：来源 leader 会话保持可见并关联 Team。
- `extra.team_id`：成员会话被普通历史和搜索过滤。

**Step 2: 校验 API 与事件**

- `POST /api/teams/from-conversation`
- `GET /api/teams/by-conversation`
- `team.created`、`team.listChanged`、`team.removed`、`team.renamed`
- Team runtime/session 和 teammate message 事件。

**Step 3: 增加兼容性测试**

测试旧数据没有 `origin_conversation_id`、旧客户端忽略新字段、成员会话缺失 `team_id` 等场景，确保升级不会阻塞普通 Team。

**上游迁移编号规则：** 每次重新集成前先检查 `crates/aionui-db/migrations/` 的最高版本。二开迁移必须使用上游最新版本之后的编号；例如官方基线已经占用 `021` 时，临时 Team 迁移应顺延到 `028`，避免 SQLite migration version mismatch。

重点回归：

- 删除 Team 后返回来源会话。

### Task 6：建立上游同步周期

建议每次官方发布后执行以下流程：

1. `git fetch upstream --prune`。
2. 更新 AionUi/AionCore `main`。
3. 创建新的 `integrate/ad-hoc-team-latest` 分支。
4. 按提交层次 cherry-pick 二开提交。
5. 先跑后端契约测试，再跑前端集成测试，最后跑全量测试。
6. 记录冲突、API 变化和需要重新设计的部分。
7. 集成分支稳定后再合并到个人 fork 的发布分支。

不要直接在长期功能分支上不断 merge 上游；长期分支应保留清晰的功能历史，集成分支用于吸收上游变化。

### Task 7：准备两个上游 PR

**PR 1：AionCore**

- 说明数据迁移、Team promotion API、事件广播、会话上下文和消息回流。
- 附后端测试命令与结果。
- 明确数据库迁移兼容性和 API 字段语义。

**PR 2：AionUi**

- 说明协作入口、状态卡、消息回流、历史过滤、侧边栏刷新和视觉区分。
- 在正文中链接 AionCore PR。
- 附前端测试、i18n 和类型检查结果。

两个 PR 都应遵循官方 `CONTRIBUTING.md`：单一主题、Conventional Commit、真实填写测试清单，不加入 AI 签名。

### Task 8：上游版本升级后的快速整合清单

本节用于以后官方仓库发布新版本、但二开 PR 尚未合并时的重复执行。

**Step 1: 记录版本和工作区状态**

```bash
# 在 AionUi 和 AionCore 各执行一次
git status --short --branch
git log -1 --oneline
git fetch upstream --prune
git log --oneline HEAD..upstream/main
```

若工作区不干净，先提交临时快照或导出补丁；不要直接切换分支覆盖改动。

**Step 2: 更新纯上游 main**

```bash
git switch main
git merge --ff-only upstream/main
```

如果无法快进，停止操作并确认是否存在本地独有提交；不得用强制 reset 覆盖它们。

**Step 3: 新建一次性整合分支**

```bash
git switch -c integrate/ad-hoc-team-YYYYMMDD
```

从 `feat/ad-hoc-team-context` 中按逻辑提交 cherry-pick。AionCore 先于 AionUi 整合，以便先确定 API、事件和数据库契约。

**Step 4: 解决冲突并检查契约**

- 先处理 AionCore 的迁移、Team DTO、promotion service 和广播事件。
- 检查迁移最高编号，二开迁移使用上游最新编号之后的版本。
- 再处理 AionUi 的 mapper、hook、Team 页面、历史过滤和 i18n。
- 冲突解决后运行 `git diff --check`，确认没有误删上游逻辑。

**Step 5: 分层验证**

```bash
# AionCore
cargo test -p aionui-db -p aionui-team -p aionui-api-types

# AionUi（必须使用 package.json engine 要求的 Node 版本，例如 Node 22）
pnpm exec vitest run <临时 Team 相关测试文件>
pnpm run i18n:types
node scripts/check-i18n.js
pnpm exec tsc --noEmit
```

再执行人工冒烟：普通会话建 Team、上下文继承、消息回流、侧边栏即时显示、临时 Team 图标、删除后返回来源会话。

**Step 6: 记录结果并决定发布方式**

- 所有重点测试通过：保留整合分支，准备 AionCore/AionUi 两个 PR。
- 只有预存环境失败：在报告中列明失败命令、错误位置和“与本次变更无关”的证据。
- 出现行为回归：不要合并到发布分支，回到冲突提交逐项修复。
- 上游长期无回应：继续维护 fork 和整合分支，不修改 `main` 的上游跟踪职责。

**Step 7: 建立可回滚点**

```bash
git tag ad-hoc-team-sync-YYYYMMDD
git branch backup/ad-hoc-team-sync-YYYYMMDD
```

只有在测试和人工冒烟完成后才创建发布 tag；回滚时回到该 tag 或重新从 `upstream/main` 构建整合分支。

## 4. 回滚与故障处理

### 4.1 集成失败

1. 保留冲突现场日志。
2. 放弃当前 integration 分支，重新从最新 `upstream/main` 创建临时分支。
3. 逐个 cherry-pick，定位具体不兼容提交。
4. 修复后追加新提交，不重写已对外共享的功能分支历史。

### 4.2 功能回滚

- AionUi 与 AionCore 必须成对回滚，避免前端调用不存在的 API 或后端返回无法解析的字段。
- 数据库迁移一旦发布，不删除已创建的列；通过兼容读取或后续迁移处理。
- 如果只需要暂时关闭入口，优先使用功能开关隐藏 UI，不删除后端数据契约。

### 4.3 上游拒绝或长期无回应

继续在个人 fork 中维护功能分支，并定期从上游同步。对外沟通使用“可运行 prototype / 已准备 PR / 等待范围确认”的表述，不宣称官方已经接受合并。

## 5. 验收标准

- 两个仓库的 `main` 可以独立快进到官方最新版本。
- 功能分支只包含临时 Team 连续上下文相关提交。
- 从最新上游基线可以通过 cherry-pick 重建功能。
- AionUi 与 AionCore 的字段、API、事件语义一致。
- 重点回归测试全部通过；预存环境失败被单独记录。
- 任何一次集成冲突都能通过分支删除并重新构建恢复。
- 可以分别提交 AionCore 和 AionUi PR，并在 PR 中互相链接。

## 6. 推荐执行顺序

当前建议按以下顺序推进：

1. 先冻结当前原型并保存两个仓库的 commit SHA。
2. 将现有改动整理成 AionCore/AionUi 的逻辑提交。
3. 更新两个仓库的 `main` 到官方最新版本。
4. 从最新基线建立 integration 分支并重新 cherry-pick。
5. 运行验证矩阵并记录差异。
6. 再决定是继续内部维护，还是正式向两个官方仓库提交 PR。

完成一次整合后，下一次升级只需从 **Task 8** 开始；不要重复修改已验证的功能分支，也不要把整合分支反向合并回纯上游 `main`。
