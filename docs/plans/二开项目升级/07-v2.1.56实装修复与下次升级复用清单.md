## 1. 最终人工验收结论

2026-08-18 手工复测确认：

1. 普通会话创建 ad-hoc Team 后，来源页状态不再立即显示“已解散” —— **已解决**；
2. ad-hoc Team 中 Aion/assistant 不再无条件落到 `default` 模型 —— **已解决**；
3. ad-hoc Team 名称按来源会话生成，不再全部固定为同名 —— **已解决**；

## 2. 为什么仅按 PIN 重放仍然不够

原版资产 PIN 能保证“原始二开能力”不丢，但不能保证后续开发分支中已经修过的回归缺陷不会再次出现。

本轮最终证明：在原始 PIN 之后，ad-hoc Team 还出现过多次重要修复；如果升级时只按 PIN 或早期 redo tip 机械恢复，就会把这些缺陷重新带回来。

因此下次升级必须增加一个固定阶段：

> **扫描 PIN → 最终二开开发分支之间所有与目标模块相关的后续提交，建立“后 PIN 修复补遗清单”。**

不能只看 feature commit，也必须扫 `fix(...)`、测试补丁、迁移修复、UI 身份语义和生命周期补丁。

## 3. 本轮确认的重要后 PIN 修复

### 3.1 AionUi

#### `546113740 fix(team): keep ad-hoc teams active after creation`

这是“创建后立即已解散”的直接历史修复。

核心语义：

- backend 返回空 `team_id` 的“无关联 sentinel”时，mapper 必须返回 `null`；
- 创建成功后，hook 必须重新写入完整 association：
  - `team_id`
  - `origin_conversation_id`
  - `status: active`
- 禁止沿用 create 前旧 association 的 `disbanded` 状态。

对应回归测试应保留：

- `returns null for the backend no-association sentinel`
- `marks a newly created team active when the previous lookup reported disbanded`

#### `0a0d8aba9 fix(team): preserve same-name team identities`

此提交证明 Team 列表/操作必须始终以 `team.id` 为唯一身份，不得按 display name 识别。

下次升级需检查：

- React key = `team.id`
- rename/delete/select 都以 id 操作
- 同名 Team mapper 不去重
- 建议保留 `data-team-id` / `data-testid=team-item-${team.id}` 作为 DOM 回归抓手

#### `d657207c7 fix(team): name ad-hoc teams from source conversations`

命名规则应由来源会话参与，而不是后端统一 fallback：

```text
来源会话标题 · 临时团队
```

若来源标题为空，才退回本地化“临时团队”。

本轮实践中，命名问题与“侧栏不即时刷新”问题曾叠加，容易误判为同一个 bug。下次要分别测试：

1. 创建出的 Team name 是否正确；
2. Team list 是否立即出现。

### 3.2 AionCore

#### `6edd36c0 fix(db): atomically unbind deleted team origin`

删除 ad-hoc Team 时，来源 conversation 不能只“保留不删”，还必须原子清除 Team-only metadata。

应清理：

```text
teamId
team_id
slot_id
role
team_mcp_stdio_config
```

但只能在现有 marker 仍指向待删除 Team 时清理；若 conversation 已重新绑定到另一 Team，必须冲突失败，禁止误清。

#### `d7481360 fix(team): unbind origin conversation on team removal`

`remove_team()` 跳过 origin conversation 删除后，必须显式调用 unassign。

关键顺序：

```text
停止 session / worker
→ 删除非 origin teammate conversations
→ unassign origin conversation
→ 删除 mailbox/tasks/team
```

#### `5e25a729 fix(db): clean orphaned team conversation bindings`

新代码只能防止未来继续制造脏数据，不能修复历史已经残留的 orphan marker。

本轮 v0.1.67 当前 migration 已占用 039/040/041，因此一次性 cleanup 不能继续照抄旧 041，必须按“当前官方/二开 max + 1”新增。

本轮最终编号：

```text
042_remove_orphaned_team_conversation_bindings.sql
```

规则：只清理 marker 指向不存在 Team 的 conversation；存在真实 Team 的绑定必须保留。

#### `722e5315 + c689c48d`

这组是“ad-hoc Team 存在期间，来源普通会话在 Team idle 时仍可普通聊天”的行为增强与并发安全配套。

本轮未把它列为 P0，因为人工验收阶段允许先保持来源会话被 Team 接管。

但如果未来要恢复该体验，**两者必须作为一组恢复**：

- `722e5315`：允许符合条件的 origin lead idle solo turn；
- `c689c48d`：普通 turn 与 team run 互斥/串行化，避免 check-then-act race。

禁止只移植前者。

## 4. 本轮新增发现：ad-hoc 创建没有广播 `team.created`

这是本轮手工验收后新发现的独立历史缺陷。

现象：

- ad-hoc Team 已创建成功；
- 可以直接进入 Team 页面；
- 但左侧 Team 列表不立即出现；
- 需要等某个后续事件、刷新或重新拉取后才出现。

根因：

普通 Team 创建路径会：

```text
broadcast_team_created(user_id, team_id, team_name)
```

而 ad-hoc `create_ad_hoc_team_from_conversation()` 创建成功路径此前没有发 `team.created`。

AionUi `useTeamList()` 已经正确订阅：

```text
team.listChanged
team.created
team.removed
team.renamed
```

并在收到事件后 `mutate()`；真正缺的是 Core 事件广播。

修复要求：

- ad-hoc Team 真正新建成功后广播一次 `team.created`；
- idempotent reuse 分支不能重复广播“创建”事件；
- integration test 应断言首次创建恰好产生一次 `team.created`。

**下次升级固定检查：所有新增/删除/重命名等写路径必须核对 WS/list cache invalidation 事件，不要只验证 API 返回。**

## 5. 模型继承：不能再出现硬编码 `default`

本轮 v0.1.67 redo 中，ad-hoc 创建路径曾在三个位置直接写：

```rust
model: "default".into()
```

覆盖：

1. reused origin leader；
2. 初次创建的 target teammate；
3. existing ad-hoc Team 后续追加 target。

这会绕过 Assistant 自身的模型配置与正式 Team 的选择语义。

最终修复原则：

### 5.1 Team selectable assistant catalog 必须携带“已解析 preferred model”

单 assistant detail 解析应遵循：

```text
fixed default
  → fixed value

auto default
  → preference.last_model_id（若存在）

仍为空
  → backend default/fallback
```

不要简单替换成“第一个 enabled provider model”。

### 5.2 ad-hoc 三条创建路径统一消费同一结果

- leader
- initial target
- add target to existing team

都不得再各自拼模型规则。

### 5.3 回归测试至少覆盖

- leader 使用 preferred model；
- target 使用 preferred model；
- fixed / auto(last_model_id) 的优先级；
- fallback 时才允许 backend default。

## 6. 一个非常容易误判的运行时陷阱：`cargo check` 不等于重编最终 binary

本轮人工验收曾出现：

- 源码已经改好；
- Rust unit/integration test 通过；
- `cargo check -p aionui-app` 通过；
- 用户重启 `bun run dev`；
- 实际行为仍然是旧逻辑。

最终查明：

```text
target/debug/aioncore
```

可执行文件的 mtime 仍然是前一天，说明 `cargo check`/测试没有重新产出 Dev 启动实际引用的最终 binary。

### 6.1 正确 Dev 验收步骤

Core 代码有任何修改后，手工验收前必须显式执行：

```bash
cd /Volumes/KINGSTON/CodeVault/GitHub/AionCore-upgrade-<version>
cargo build --bin aioncore
```

若 shell PATH 不完整，使用实际 Rust toolchain 的 cargo 绝对路径。

然后确认 binary 时间戳：

```bash
stat -f '%Sm %N' target/debug/aioncore
```

再完整停止旧 AionUi Dev / AionCore 主进程，重新运行：

```bash
cd /Volumes/KINGSTON/CodeVault/GitHub/AionUi-upgrade-<version>
AIONUI_BACKEND_BIN="/Volumes/KINGSTON/CodeVault/GitHub/AionCore-upgrade-<version>/target/debug/aioncore" bun run dev
```

最后核对真实进程 command line 指向预期 binary。

### 6.2 固定结论

> `cargo check` 用于编译检查；`cargo test` 用于测试目标；**人工 Dev 验收前必须确保 `cargo build --bin aioncore` 已真正刷新最终可执行文件。**

以后看到“源码测试都过了，但 UI 行为像旧版本”，先查 binary mtime / PID / command line，不要先怀疑浏览器缓存。

## 9. 下次升级的固定执行顺序

### S0：冻结证据

- 记录新 AionUi/Core upstream tag + SHA；
- 记录当前最终二开分支 tip；
- 记录原始 PIN；
- 禁止一开始就 cherry-pick。

### S1：资产与后 PIN 补遗双扫描

同时做两套扫描：

1. PIN 资产清单：回答“原始功能有哪些”；
2. PIN → 最终二开 tip：回答“原始功能之后还修过什么”。

后者必须按模块路径 + commit message 双重搜索。

### S2：上游差异审计

逐宿主锚点判断：

- 可直接复用；
- 需要 adapter；
- 上游架构已替代；
- 上游原生实现可删除二开。

### S3：Core 先行

顺序：

```text
API/DB model
→ migrations + repair
→ repository
→ provisioning/service
→ routes
→ focused tests
→ cargo check
→ cargo build --bin aioncore
```

### S4：UI 分层

```text
shared types/bridge
→ i18n
→ A 级模块
→ B 级 slot
→ C 级宿主三方合并
→ focused tests
```

### S5：事件与缓存一致性专项

所有 mutation path 检查：

- DB/API 是否成功；
- WS event 是否发出；
- AionUi SWR/cache 是否订阅并 invalidate；
- route 当前页是否能立即看到状态；
- sidebar/history 是否立即同步。

不要只验证“刷新后是对的”。

### S6：手工生命周期验收

每个 ad-hoc Team 至少完整跑：

1. solo conversation 创建；
2. 创建 ad-hoc Team；
3. 当前来源页状态立即 active；
4. Team 侧栏立即出现；
5. 名称正确；
6. leader/target 模型正确；
7. 切入 Team；
8. 运行一次 Team task；
9. 切回来源会话；
10. 删除 Team；
11. 来源会话 marker 清除；
12. 来源会话重新可普通发送；
13. 再创建一个新 ad-hoc Team，验证没有残留锁。

### S7：旧数据升级验收

至少准备：

- fresh DB；
- 上一轮 redo DB；
- 更老 PIN-era DB。

验证 migration remap + orphan cleanup 后均能启动。

## 10. 升级完成前的禁止项

- 禁止把 PIN 当成“最终正确实现”；
- 禁止只扫 feature commits，不扫后续 fixes；
- 禁止整文件覆盖高风险 Core `service.rs/provisioning.rs`；
- 禁止按 Team name 识别实体；
- 禁止 ad-hoc 模型硬编码 `default`；
- 禁止删除 Team 时只“跳过 origin 删除”却不 unassign；
- 禁止 mutation 成功却不检查 WS/cache invalidation；
- 禁止看到 `cargo check` 通过就默认 Dev binary 已更新；
- 禁止在未重新 build + restart 的情况下进行最终人工行为验收；
- 禁止迁移号直接沿用上一版本，必须每次重新读取当前 max。
