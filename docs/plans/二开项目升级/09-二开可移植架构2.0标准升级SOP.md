# 二开可移植架构 2.0 标准升级 SOP

> 状态：正式基线
> 建立日期：2026-08-19
> 前置架构方案：`08-AionTeamSuite二开可移植架构2.0优化方案.md`
> 权威二开资产仓：`/Volumes/KINGSTON/CodeVault/GitHub/AionTeamSuite`

## 1. 目的

本 SOP 用于后续每一次 AionUi / AionCore 上游升级。目标不是再次人工重放历史二开代码，而是优先使用 AionTeamSuite 2.0 已建立的可移植能力：

1. Upgrade Doctor：升级前识别机器可证明项与人工 Host Slot；
2. Owned Runtime materialize：原样同步 AionTeamSuite authoritative runtime；
3. Upgrade Overlay：基于“旧 upstream → 已验证 portable implementation → 新 upstream”做三方合并；
4. Semantic Migration Compiler：根据新 upstream 最大 migration 自动编号并生成 SQL；
5. Generic Repair Runner：识别历史已验证 target window，并在生产数据库副本上安全 remap SQLx metadata；
6. Focused / crate / full regression；
7. 生产数据库 preflight；
8. 构建、安装、人工验收；
9. 稳定后才允许 Promote 到 `latest`。

核心原则：

> 新版升级首先是“自动重放 + 兼容性核验”，只有真正的 `CONFLICT` / Doctor `RED` 才进入人工重新理解和编码。

## 2. 永久边界

### 2.1 权威源码归属

AionTeamSuite 是二开 authoritative source。

UI owned runtime：

```text
AionTeamSuite/runtime/ui/
```

Core owned runtime：

```text
AionTeamSuite/runtime/core/team/
```

AionUi / AionCore 中对应 package / portable module 是 vendored/materialized 副本，不能形成第二套人工维护源。

### 2.2 禁止直接依赖本机绝对路径

禁止让 AionUi/AionCore build 直接引用：

```text
../../AionTeamSuite
/Volumes/.../AionTeamSuite
```

正式宿主必须使用 materialized/vendor 文件，保证独立构建、CI、换机可恢复。

### 2.3 生产候选与架构工具分离

每次升级创建独立 candidate branch/worktree。

禁止在：

- 当前稳定生产分支；
- `latest`；
- 用户正在使用的正式安装包对应候选

上直接做探索性架构修改。

### 2.4 禁止直接操作真实生产数据库做开发验证

Migration/repair 开发、dry-run、apply 测试必须先使用：

- synthetic DB；或
- SQLite `.backup` 得到的生产数据库副本。

只有在正式生产升级 Gate 通过后，才能对真实生产 DB 执行明确的 repair/preflight 流程。

### 2.5 migration 编号不属于稳定资产

稳定资产是 migration semantic id / SQL 语义，不是 `039/040/...` 数字。

禁止人工沿用旧编号。新版本必须由 compiler 根据新 upstream 最大 migration 自动重新分配。

## 3. 每轮升级的输入

开始前必须明确四个版本：

```text
OLD_UI_UPSTREAM
OLD_CORE_UPSTREAM
NEW_UI_UPSTREAM
NEW_CORE_UPSTREAM
```

同时明确最近一组已验证 portable implementation：

```text
VALIDATED_UI_PORTABLE_REF
VALIDATED_CORE_PORTABLE_REF
```

以及生产数据库路径（仅供后续 preflight，不在初始阶段修改）：

```text
PRODUCTION_DB
```

必须验证 AionUi 新版 `package.json` 的 `aioncoreVersion` pin 与计划 Core 版本一致。

# Gate A：建立干净新宿主

## A1. 创建独立 worktree

UI / Core 分开建立，基于新 upstream tag/SHA。

要求：

- 不覆盖旧 candidate；
- 不 destructive reset；
- 不修改 `latest`；
- 记录 base SHA。

## A2. 记录初始 Git 状态

至少保存：

```bash
git status --short
git rev-parse HEAD
git describe --tags --always
```

Gate A 通过条件：新宿主是可识别、可回滚、与旧生产候选隔离的独立工作区。

---

# Gate B：编码前 Upgrade Doctor

在任何二开代码 materialize 前运行：

```bash
ruby AionTeamSuite/scripts/upgrade-doctor.rb \
  <NEW_UI_ROOT> \
  <NEW_CORE_ROOT> \
  [PRODUCTION_DB_COPY]
```

Doctor 结果解释：

- `GREEN`：机器可证明兼容；
- `YELLOW`：文件/锚点存在，但签名或宿主语义必须人工 review；
- `RED`：缺少 runtime、port、adapter wiring、generated metadata 或出现确定冲突。

禁止把“文件存在”当作接线成功。Doctor 必须覆盖 package/crate registration 和 adapter wiring。

需要保存初始结果，作为本次升级“预测工作量”基线。

---

# Gate C：Migration Preflight

## C1. 生成新版本 migration plan

```bash
ruby AionTeamSuite/scripts/migration-compiler.rb plan <NEW_CORE_ROOT>
```

确认：

- upstream max；
- semantic migration 新编号；
- 不存在重复 upstream version。

## C2. 对生产 DB 副本做 preflight

先 SQLite backup，再：

```bash
ruby AionTeamSuite/scripts/migration-compiler.rb \
  preflight <NEW_CORE_ROOT> <DB_COPY>
```

可能结果：

- `fresh`
- `current`
- `partial-target`
- `repair-required`
- hard failure（foreign/suspicious/collision）

若出现 `repair-required`，source window 必须来自 compiler 已知 historical identities；未知 metadata 禁止自动修。

## C3. 历史 validated target 必须进入版本链

每次完成并生产验证一组新 target 后，其 version + description + checksum 必须登记为下一轮 historical identity。

这样下一版 upstream 消耗旧二开编号时，compiler 可以自动生成：

```text
old validated target → new target
```

而不是报成未知 foreign target。

# Gate D：Owned Runtime Materialize

UI：

```bash
ruby AionTeamSuite/scripts/materialize-ui-runtime.rb <NEW_UI_ROOT>
ruby AionTeamSuite/scripts/verify-ui-runtime-materialization.rb <NEW_UI_ROOT>
```

Core：

```bash
ruby AionTeamSuite/scripts/materialize-core-runtime.rb <NEW_CORE_ROOT>
ruby AionTeamSuite/scripts/verify-core-runtime-materialization.rb <NEW_CORE_ROOT>
```

验收要求：authoritative 与 vendored 文件 SHA 一致。

原则：

> Owned code 不重新编码，不通过手工 copy/paste 迁移。

---

# Gate E：Upgrade Overlay

使用：

```bash
ruby AionTeamSuite/scripts/upgrade-overlay.rb plan \
  <SOURCE_REPO> <OLD_UPSTREAM_REF> <VALIDATED_PORTABLE_REF> <NEW_HOST_ROOT> \
  [EXCLUDE_PREFIX ...]
```

确认结果后才执行 `apply`。

状态含义：

- `COPY`：旧 upstream 未变化或 portable 新文件，可直接复用；
- `MERGE`：Git 三方合并干净；
- `SAME`：新宿主已具备相同内容；
- `DELETE`：portable 删除且新宿主未改；
- `EXCLUDED`：交给专用 generator；
- `CONFLICT`：必须人工处理。

### 必须排除的 generated 文件

典型：

- 动态编号 migration SQL；
- generated repair plan；
- `i18n-keys.d.ts` 等可标准生成产物。

这些文件禁止当作普通三方 merge 冲突处理。

### 人工工作范围

人工/AI 只处理：

1. `CONFLICT`；
2. Doctor `RED`；
3. Doctor `YELLOW` 的 Host Slot 签名/语义 review。

如果没有 conflict，不允许为了“保险”重新手写已经 clean merge 的 owned/adapter 业务逻辑。

---

# Gate F：Materialize Migration + Repair Metadata

## F1. 生成 SQL

```bash
ruby AionTeamSuite/scripts/migration-compiler.rb render \
  <NEW_CORE_ROOT> <TEMP_OUTPUT>
```

再把 compiler 产物 materialize 到新 Core migration 目录。

## F2. 生成 repair metadata

```bash
ruby AionTeamSuite/scripts/migration-compiler.rb repair-shell \
  <NEW_CORE_ROOT> \
  <NEW_CORE_ROOT>/scripts/migration/generated-2dev-team-migration-plan.sh
```

Core repair runner 本体必须保持 generic，不允许重新写死数字窗口。

## F3. DB 副本 repair 演练

必须执行：

```text
dry-run
→ apply on DB copy
→ post-check metadata
→ normal AionCore migrator
```

最终确认：

- upstream migration 占用它自己的编号；
- semantic custom migrations 位于新分配窗口；
- 全部 `success=1`；
- 用户数据没有被重建或整体复制替换。

---

# Gate G：Generated Artifacts

所有被 overlay `EXCLUDED` 的生成文件必须执行项目原生 generator。

UI i18n 示例：

```bash
bun run i18n:types
node scripts/check-i18n.js
```

不得手工维护生成文件来绕过 generator。

---

# Gate H：Focused Verification

## UI

至少执行：

```bash
bunx tsc --noEmit --project tsconfig.json
```

以及 AionTeamSuite capability 对应 focused tests。

必须覆盖：

- ad-hoc create/reuse/status；
- preferred model；
- source conversation naming；
- sidebar realtime；
- delete/unbind；
- Team Presets；
- history/grouping；
- Aionrs teammate backflow。

## Core

至少：

```bash
cargo check -p aionui-team
cargo test -p aionui-team
cargo clippy -p aionui-team -- -D warnings
cargo fmt --all -- --check
```

Migration / DB repository targeted tests必须额外执行。

如果测试失败，先判断：

- implementation regression；
- new upstream contract change；
- test harness/dependency mismatch。

禁止通过弱化断言让测试变绿。

---

# Gate I：Post-adaptation Doctor

再次运行 Upgrade Doctor。

目标：

```text
RED = 0
```

YELLOW 可以存在，但每一个 Yellow 都必须有人工 review 结论。

保存：

```text
initial Doctor
→ adaptation
→ final Doctor
```

用于评估 Doctor 预测准确率。

---

# Gate J：全量验证

Focused Gate 全绿后才能进入全量：

UI：项目标准 full test。

Core：受影响 workspace / full workspace gate，按项目 AGENTS/testing 规则执行。

必须区分：

- 本轮二开回归；
- 新 upstream 自身已有 baseline failure。

不能把 baseline bug 算成本次升级责任，也不能用 baseline bug 掩盖二开回归。

---

# Gate K：Production Candidate Build

只有以上 Gate 全绿后才构建真实 candidate。

必须核对：

1. AionUi version；
2. bundled Core version；
3. bundled Core sourceType；
4. Core git commit；
5. bundled Core SHA256；
6. package SHA256；
7. macOS signing/notarization 状态。

特别规则：

> AionUi backend packaging 的 local-binary 参数不一定优先于 release/download 路径，必须检查最终 embedded manifest 与 binary SHA，不得只相信 build command。

---

# Gate L：真实生产 DB Preflight

在正式安装 candidate 前：

1. 停止旧应用/确认没有并发 migrator；
2. 读取真实 `_sqlx_migrations`；
3. compiler preflight；
4. dry-run repair；
5. 创建 SQLite backup；
6. `--apply`；
7. 启动新版 normal migrator；
8. 再次读取 migration metadata。

严禁：

- 删除数据库；
- 用新空库替换；
- 整库“同步”；
- 手工改 SQLx metadata 而没有 whitelist/checksum/transaction。

---

# Gate M：人工生产验收

至少验证：

1. 创建 ad-hoc Team 后立即 active；
2. leader/target 模型继承正确；
3. source conversation 命名正确；
4. 同名 Team 以 ID 区分；
5. Sidebar 实时出现；
6. 删除 ad-hoc Team 后 source conversation 保留且解绑；
7. Team Presets CRUD / invoke；
8. 普通 conversation/history 无回归；
9. app restart 后 migration 不重复失败。

Production DB repair backup 必须保留到人工验收结束。

---

# Gate N：Promote / Latest

只有满足以下条件才能把产品代码晋升：

```text
Focused tests ✅
Full tests / baseline accounting ✅
Production DB migration ✅
Package verification ✅
Manual production acceptance ✅
```

之后才允许：

```text
candidate → latest
```

`latest` 不是开发试验分支，也不是“代码写完就自动晋升”的分支。

文档/SOP 可以提前更新到 latest；产品代码不行。

## 4. 每轮升级必须产出的证据

每一轮至少归档：

```text
1. old/new upstream refs
2. initial Doctor report
3. migration plan
4. overlay report
5. conflict list + 处理结论
6. final Doctor report
7. focused test results
8. full test / baseline failure accounting
9. DB preflight / repair / final metadata
10. package manifest + hashes
11. manual acceptance result
12. final integration commits
```

推荐存放：

```text
AionTeamSuite/docs/verification/YYYY-MM-DD-<target>-upgrade-acceptance.md
```

对应 target-specific adaptation 可放：

```text
AionTeamSuite/packages/adaptations/<ui>-<core>/
```

## 5. 成功指标

每轮升级结束时统计：

### Owned Runtime reuse

目标：

```text
>= 90%
```

如低于 80%，必须重新评估 portable boundary 是否退化。

### Host manual review

UI 目标：

```text
<= 8 个明确宿主检查点
```

Core 目标：

```text
少量稳定 registration/port/adapter 接点
```

### Migration

```text
编号自动分配       100%
collision preflight 100%
SQL semantic generate 100%
```

### 重新编码

目标不是追求“0 行”作为硬指标，而是：

> 只有真实上游 contract 变化或 merge conflict 才重新编码；不得因为升级流程本身而重复实现 owned business logic。
