本报告基于以下既有权威资产：

判定四档：

- ✅ **可直接复用**：二开模块本体或接点在 v2.1.56/v0.1.67 仍可按原形复用，最多只有机械 import/行号漂移；
- 🟡 **需要 adapter**：业务能力仍需保留，但宿主锚点、类型、runtime、数据库或周边逻辑发生变化，必须在新版结构中重新接线；
- 🔴 **被上游架构替代**：旧二开实现方式不应继续照搬，应改用新版上游架构承载同一业务意图；
- ⚪ **上游已原生实现可删除二开**：上游已经提供等价能力，二开重复实现应删除或不再重放。

说明：某个宿主文件可以整体判为 🟡，但其中某一小块能力（例如 ACP `teammate_message`）可单独判为 ⚪。

## 2. AionUi v2.1.52 → v2.1.56 上游变化概览

1. sidebar backend-driven grouping/paging/pin fidelity（随后主体被 `ecf1d2e8c` revert）；

#### v2.1.56

主要变化是：

1. conversation 手动标记未读；
2. ACP config option “pending_next_turn” 展示为 pending；

直接命中二开接点：`ConversationRow.tsx`、`GroupedHistory/types.ts`、`useConversationListSync.ts`、`useAcpConfigOptions.ts`。

## 5. 上游已原生实现、应去重的能力

### 5.1 Team runtime / SendBox runtime

v2.1.56 ACP 与 Aionrs SendBox 都已经原生具备：

- `teamRuntime?: TeamSendBoxRuntime`；
- `teamRuntime.runtimeGate`；
- `teamSendMessage` 分流；
- team runtime loading/status/stop/retry/elapsed UI。

因此二开不应重新造一套 Team SendBox runtime。需要保留的只是“普通会话被 promoted 后，在 Team 正运行期间如何限制/接管 source conversation”的额外规则。

判定：🔴 **旧 `isTeamRunning` 独立 prop 链属于应收敛的旧实现方式**；业务效果仍需通过新版 runtime seam 实现。

### 5.2 ACP teammate_message

`useAcpMessage.ts` v2.1.56 已原生：

- 将 `teammate_message` 列入可处理类型；
- `case 'teammate_message'` 归一化内容并 `mergeLiveMessage`。

判定：⚪ **ACP 侧重复 backflow 不应再叠加。**

Aionrs `useAionrsMessage.ts` 仍没有该 case，因此跨平台 helper 仍有价值。

### 5.3 Team WS 事件

AionUi v2.1.56 `ipcBridge.team` 已原生存在二开 full hook 依赖的 15 个核心事件：

`removed / renamed / agentStatusChanged / sessionChanged / teammateMessage / runAccepted / runStarted / runUpdated / runCompleted / runCancelled / runFailed / childTurnStarted / childTurnCompleted / childTurnCancelled / taskChanged`。

Core v0.1.67 `crates/aionui-team/src/events.rs` 同样定义这些事件。

判定：⚪ **WS 事件基础设施无需二开重复实现**；二开只消费它们。

### 6.4 `teamId` / `team_id` 契约风险

v0.1.67 `TeamSessionBinding` 仍从 conversation extra 的 `teamId` 读取 Team session binding；数据库 legacy normalize 也同时处理过 `teamId` / `team_id`。而二开资产定义要求：

- promoted source：`extra.teamId`；
- member conversation：`extra.team_id`；
- UI 对两者采取不同可见性/运行时策略。

这说明该大小写/下划线差异在 v0.1.67 不能被当作普通字段别名简单归一化。P4 必须以 redo `ce1a8bf3` 的实际写入点和 v0.1.67 TeamSessionBinding 读取规则逐条复核，避免破坏上游 Team session ownership。

判定：🟡 **高风险契约点。**

## 10. P2 结论 / S1 建议

P2 可以进入 S1：

1. **二开核心业务没有被 v2.1.56 / v0.1.67 吞并**：from-conversation、by-conversation、origin binding、Team Presets 仍然是纯二开能力；
2. **上游 runtime/WS 能力明显增强**：Team runtime、15 组 WS、ACP teammate_message 已原生，下一轮应该主动去重；
3. **最大新增迁移风险已经明确**：官方占用了 038，redo 038/039/040 必须平移；
4. **UI 大多数重做宿主结构没有净变化**：TeamCreateModal、TeamPage、TeamSiderSection、ACP/Aionrs sendbox 等仍可直接以 v2.1.52 redo 为三方适配基准；
5. **真正新增的 UI 合并风险只有三组**：Aionrs fork、GroupedHistory manual unread、ACP config pending-next-turn；
6. **GroupHistory 上游现有 team filter 不是二开等价能力**：它同时隐藏 `teamId` 与 `team_id`，必须恢复二开的 ownership 非对称规则；
7. **P4 Core 实施前必须优先审计 `fe99ff60`**，因为 v0.1.67 Team provisioning/capability resolver 是本轮 Core 最重要的新宿主变化。

S1 通过后，建议进入 P4 Core 详细适配设计，而不是直接开始 UI 搬运。
