# 二开升级与模块化改造分析报告

> 日期：2026-07-30  
> 范围：AionUi `integrate/ad-hoc-team-latest`、配套 AionCore 分支，以及上游 AionUi `v2.1.40` 至 `v2.1.44`。  
> 性质：只读分析与决策建议；不代表已实施的重构方案。

## 1. 结论摘要

建议采用“**持续侦测、窗口化升级、渐进外置策略**”的路线。

- 可以不在每个上游版本发布时都立即合并并发版，但不能停止跟踪后隔很多版本一次性合并。
- 当前二开应收敛为“薄核心桥接层 + 可外置策略/配置/扩展层”，而不是把临时团队运行能力整体改造成插件。
- 优先把角色、提示词、技能、MCP/ACP、模型策略、团队预设和独立设置页外置；会话绑定、权限、持久化、调度和运行时事件保留在核心。
- 升级前必须把 AionUi 与 AionCore 当作一个版本化整体评估、构建和验收。

## 2. 2.1.40 → 2.1.43 / 2.1.44 的上游变化与升级价值

### 2.1.40 基线

当前二开共同基线为上游 `v2.1.40`（`e9882492e`），其配套 AionCore 为 `v0.1.51`。当前 AionUi 二开分支相对上游主线已形成会话内临时团队（ad-hoc team）相关差异；AionCore 则承担其领域服务、会话适配和迁移。

### 2.1.41 至 2.1.43 的主要价值

上游在该区间包含下列与本项目直接或间接相关的改进：

- 团队运行体验：手动 warmup、成员唤醒状态、模型选择器中的 warmup 提示、相关测试修复。这与二开的团队运行状态、会话切换和事件订阅存在同一高频改动面。
- 会话与权限：ACP 会话上下文使用量恢复、一次性权限决策、长 URL/路径展示修复、ThoughtDisplay 计时持久化。
- 工作区与文件能力：项目范围 Explorer、目录优先排序、文件/目录选择器恢复、预览与前端文件访问整理。
- 技能与助手：技能删除确认语义、助手 quick-chat、启动目录创建修复。
- 桌面体验：托盘交互、快捷键、通知等改进。

`v2.1.43` 将配套 AionCore 更新到 `v0.1.54`。该升级价值不只是功能增量：团队、会话和 runtime 的持续演化意味着二开若长期停在 `v0.1.51`，未来会同时面对 UI、事件协议和后端二进制兼容三类债务。

### 2.1.44 的主要价值与风险

上游 `v2.1.44`（`f37a6187f`）将 AionCore 配套版本更新到 `v0.1.55`。相对 `v2.1.43` 的主要内容包括：

- 项目范围文件名搜索、聊天引用和 Explorer 搜索状态/传输层；
- Explorer 打开文件时预览恢复；
- 自定义标题栏关闭时遵守“关闭到托盘”；
- 技能详情页文件浏览器；
- 对应 IPC、process bridge、SendBox、Explorer、i18n 和测试改动。

该版本值得纳入升级窗口：文件搜索、技能文件浏览和预览修复是清晰的用户价值；更关键的是可将配套后端从 `v0.1.51` 推进至 `v0.1.55`。但 Explorer、SendBox、IPC bridge 和技能设置都属于上游活跃区域，应与二开的 Conversation/Team 改动分开处理并回归验证。

## 3. 当前二开的五个补丁包（A–E）

建议把已提交二开整理成可独立重放、可独立验证的五个补丁包。每个包都应有单一目的、明确依赖和测试入口，避免在长期分支混入临时文档或工作区产物。

| 包 | 内容与目录 | 边界 | 依赖 / 验收 |
| --- | --- | --- | --- |
| A. Core API 与数据 | AionCore `crates/aionui-api-types/src/team.rs`、`crates/aionui-team/src/routes.rs`、`crates/aionui-team/src/service.rs`、`crates/aionui-db/migrations/029_ad_hoc_team_origin_conversation.sql`、repository/model | 提供从源会话创建/复用团队、按源会话查询关联、`origin_conversation_id` 唯一性 | 迁移升级、所有权、幂等创建、API 契约测试 |
| B. Core 会话与运行时适配 | AionCore `crates/aionui-team/src/provisioning.rs`、`crates/aionui-app/src/router/team_conversation_adapters.rs`，及 team session/event loop 的必要事件接线 | 通过端口桥接 Conversation、workspace、runtime config、agent turn、消息投影；领域服务不直接依赖 App 实现 | 创建团队会话、暂停/取消、恢复、运行状态黑盒测试 |
| C. AionUi 协议适配 | `packages/desktop/src/common/types/team/adHocTeamTypes.ts`、`common/adapter/teamMapper.ts`、`common/adapter/ipcBridge.ts`、`common/types/team/*` | 唯一 HTTP/WS/DTO 转换出口；页面不得自行拼接 endpoint 或订阅裸事件 | request/response mapper、WebSocket payload、兼容字段测试 |
| D. AionUi 会话与团队 UI | `renderer/pages/conversation/components/ChatConversation.tsx`、`components/AdHocTeam/*`、`hooks/useAdHocTeamFromConversation.ts`、`platforms/acp/*`、`platforms/aionrs/*`、`pages/team/*`、`components/layout/Sider/*` | 在普通会话中显示协作入口和状态；复用既有团队页与发送链路 | ACP/Aionrs 创建、导航、发送、停止、并行状态 DOM 测试 |

当前 AionUi 已提交差异相对上游主线约为 95 个文件、`+7164/-95`，本地独有 16 个提交；AionCore 本地独有 5 个提交。以上分包的目标不是制造更多层，而是让升级时冲突集中在少数已知桥接点。

## 4. 模块化 / 插件化可行性结论

### 适合外置为策略、配置或扩展层

AionCore 现有 Extension Registry 能提供 assistants、agents、skills、MCP servers、ACP adapters、model providers、themes、settings tabs 和独立 WebUI 路由。以下应优先外置：

- 团队角色、系统提示词、技能组合与工作流；
- MCP 工具组合、ACP 适配器、默认模型/提供商策略；
- 行业团队模板、标签、推荐成员和可选预设；
- 专属设置、说明、运营/监控页面，以及主题和文案资源。

建议将产品差异以扩展 manifest、skills、preset 数据和独立 WebUI 承载。未来可增加一个只读 `TeamPolicyCatalog` / `TeamPresetProvider`：扩展返回团队草案，核心服务仍做可用性、权限和持久化校验。

### 必须保留的核心桥接层

- AionCore `aionui-team` 的创建、绑定、会话 provisioning、调度、队列、暂停/取消、运行时 token 和事件投递；
- AionCore `team_conversation_adapters.rs` 对 conversation/workspace/runtime 的防腐适配；
- 数据库 migration、模型和 repository；
- AionUi `adHocTeamTypes`、`teamMapper`、`ipcBridge` 作为唯一协议层；
- AionUi 对会话 Header、发送/停止状态和团队运行事件的最薄 host adapter。

这些部分关乎权限、已有数据、消息生命周期和跨进程协议。现有扩展机制没有提供写数据库、接管 TeamSession、向既有 SendBox 注入执行逻辑，或把任意组件插入 ChatConversation 的通用能力；强行插件化会形成不可见耦合。

### 暂时不建议改动

- 不把 `session.rs`、`event_loop.rs`、scheduler 或 runtime team tools 变成可执行插件；
- 不复制 `ChatConversation`、`AcpSendBox`、`AionrsSendBox` 成扩展版本；
- 不在缺少契约测试前改写数据库升级链；
- 不先搭建泛化页面注入框架。应先验证窄接口：Header action、状态面板、send runtime gate 和 preset provider。

## 5. 为什么采用窗口化升级

“窗口化”指持续观察和合并演练，但按产品窗口集中完成冲突处理、兼容验证和发布；并不等于停止同步。

### 前提

- 保持一个纯上游基线和一个产品集成分支；
- 为 AionUi/AionCore 建立兼容矩阵：UI 版本、`aioncoreVersion`、API/WS capability、最低 migration；
- 每个上游 minor 至少执行 fetch、差异分类和 merge rehearsal；
- 核心协议、迁移、运行时事件均有契约或端到端测试。

### 收益

- 避免为了每个小版本重复发布和人工回归；
- 把冲突处理集中在固定维护窗口；
- 随着 A–E 分包和策略外置，窗口内的实际代码重放范围会逐步缩小。

### 风险与例外

- 不应跨越安全修复、数据迁移、AionCore API/WS 破坏性变更而等待窗口；这些应立即评估和跟进。
- ChatConversation、Sider、TeamPage、Acp/Aionrs SendBox 属于上游高频改动面，积累多个版本后的冲突往往是状态时序和行为回归，而非单纯文本冲突。
- 双仓版本不一致可能造成前端编译通过、运行时却与打包的 AionCore binary 不兼容。

建议节奏：每个上游 minor 做演练；每 2–4 个上游版本或一个产品发布窗口集中集成、完整回归和发版。

## 6. 推荐升级顺序与风险热点

### 推荐顺序

1. **建立干净基线**：隔离当前共享 worktree 的未提交 TeamPreset 等进行中改动；记录 `v2.1.40`、当前二开 HEAD、`v2.1.44` 和配套 AionCore 版本。
2. **先升级 AionCore**：以包 A、B 为序合并/重放，先解决 migration 序号/语义、API types、TeamService 和 conversation adapter；使用迁移及服务 E2E 验证。
3. **再升级 AionUi 通用上游能力**：先处理 `v2.1.41–v2.1.44` 的 IPC、Explorer、Skills、tray 等非临时团队变更；`package.json` 同步锁定配套 `aioncoreVersion`。
4. **重放 AionUi 协议层**：包 C 的 DTO、mapper、HTTP/WS bridge；以 API capability 为准，避免页面兼容分支扩散。
5. **最后重放会话和团队 UI**：包 D，依次处理 ChatConversation、ACP/Aionrs Chat/SendBox、Sider/TeamPage；以行为测试而非视觉比对作为主验收。
6. **成对验证与发布**：执行包 E 的构建、重点 DOM/契约测试、AionCore route/service/migration E2E，以及“创建团队→运行→暂停/取消→恢复→升级”的黑盒流程。

### 风险热点

| 热点 | 原因 | 控制措施 |
| --- | --- | --- |
| DB migration | 编号、字段语义、既有用户数据不可逆 | 先升级 Core；migration E2E；不让扩展写 DB |
| AionUi/AionCore API 与 WebSocket | 两仓独立演进、binary 打包版本锁定 | capability/版本矩阵；协议 mapper 单入口；成对构建 |
| Conversation Header / SendBox | 上游高频 UI 和运行状态变化 | 将临时团队逻辑收敛为 feature facade；覆盖发送/停止/并行状态 |
| TeamPage / Sider | 导航、缓存、事件订阅容易被上游布局变更破坏 | 先重放协议，再重放 UI；订阅事件归一化 |
| Explorer / Skills 的 2.1.44 变更 | 涉及 IPC、process bridge、文件访问和 i18n | 与团队补丁分包合并；单独跑文件搜索/预览/技能页测试 |

## 7. 短期执行清单（1–2 个迭代）

- [ ] 将 `useAdHocTeamFromConversation` 及其展示类型收敛为独立 `teamConversation` feature facade；`ChatConversation` 只保留调用点。
- [ ] 保持 `teamMapper.ts` 与 `ipcBridge.ts` 为唯一协议出口，禁止新增页面级 API 调用和裸 WebSocket 订阅。

- [ ] 建立 AionUi/AionCore 版本兼容表和升级 checklist；每个上游 minor 执行合并演练。

## 8. 最终建议

近期最有价值的投资不是“大规模插件化重写”，而是缩薄 A–D 的桥接边界、完善 E 的配套测试，并立刻外置低风险的策略资产。这样既能获得 `v2.1.43/v2.1.44` 的功能和后端升级价值，也能让未来的窗口化合并成为可预期、可验证的维护工作。
