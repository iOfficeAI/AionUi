# 二开补丁包维护与窗口化升级实施任务清单

> **依据**: 本清单基于 2026-07-30 完成的两项只读调研：
> - 「AionUi/AionCore 从 2.1.40 跟进到 2.1.43 的上游变化与跟进风险」（git/tag/log/diff + merge-tree 冲突模拟）
> - 「当前二开改动的补丁包分组与升级热点」（A/B/C/D/E 五包划分）
>
> **分析基线**: AionUi `integrate/ad-hoc-team-latest`（version 2.1.40 / aioncore v0.1.51，领先 upstream/main 16 commits + 未提交改动）；调研时 upstream/main 已推进至 2.1.44 / aioncore v0.1.55。

---

## 1. 总体目标

在不阻塞官方 AionUi/AionCore 更新的前提下，将当前二开改动固化为 **5 个可独立维护的补丁包（A/B/C/D/E）**，并建立「**窗口化升级**」流程：以上游 minor 版本为升级窗口，按固定顺序应用补丁包，每窗口产出可验证、可回滚的整合结果。

成功标志：

- 任意上游 minor 更新到达后，能在 1 个工作日内完成窗口合并并通过验收。
- 真正需要人工投入的只有补丁包 A（ad-hoc team 上下文保留）的 conversation 平台层与 TeamPage；其余为机械合并。
- 每个补丁包的文件清单、冲突热点、检查项都有据可查，新成员可按单执行。

## 4. 窗口化升级顺序

### 每个窗口的固定操作顺序

1. **侦测**：获取上游 minor/tag 和配套 AionCore 版本，更新差异/冲突台账。
2. **准备**：冻结干净基线，隔离未提交实验和非运行时文档。
3. **机械应用**：D → B，先处理依赖与 ACP 类型兼容，完成最小类型回归。
4. **核心合并**：先 AionCore，再按 A 的协议层 → 会话 UI → Team/Sider 顺序重放 AionUi。
5. **策略收尾**：C 作为追加式变更最后集成；未成熟时可从本窗口拆出，不影响核心升级。
6. **发布收口**：E 记录兼容矩阵、测试证据和回滚点，执行配套 binary 的全链路验证。

### 版本节奏

- 每个上游 minor：完成侦测、差异分类和 merge rehearsal。
- 每 2–4 个上游版本或一个产品发布窗口：完成上述完整合并、验证和发布。
- 安全修复、数据迁移、AionCore API/WS 破坏性变化：不等待窗口，应立即评估并单独跟进。

## 5. 全局验收门禁

- [ ] AionUi `package.json` 中 `aioncoreVersion` 与实际打包 AionCore binary 一致。
- [ ] AionCore migration 从历史用户数据升级后可读取 `origin_conversation_id`，且幂等/唯一性符合预期。
- [ ] `from-conversation`、按会话查询、Team WebSocket 事件与前端 mapper 的契约验证通过。
- [ ] ACP 与 Aionrs 均完成“创建团队 → 运行 → 发送 → 停止/取消 → 恢复”的行为验证。
- [ ] TeamPage、Sider、GroupedHistory 的跳转、重命名、删除和状态同步通过回归。
- [ ] TeamPreset 不改变已有 ad-hoc team 的持久化和运行时语义。
- [ ] 所有新增用户文案均已纳入现有 i18n 流程，且没有将本地工具目录/工件纳入提交。

## 6. 主要风险与决策规则

| 风险热点 | 决策规则 |
| --- | --- |
| 数据迁移冲突 | 先停在 AionCore，修复 migration/E2E 后才允许进入 AionUi UI 合并。 |
| API 或 WS schema 失配 | 视为阻塞发布；不得用页面级兼容分支绕过 mapper。 |
| Chat/SendBox 合并冲突 | 保留上游主流程，重新挂接最小 team facade；不得直接覆盖上游整个组件。 |
| C 包未成熟 | 允许延期；D、B、A 和 E 可独立完成窗口升级。 |
| 上游安全或破坏性变更 | 跳过常规窗口节奏，立即创建紧急升级窗口。 |

## 7. 完成定义

本清单完成不等于已进行一次升级。首次窗口完成的定义是：D、B、A、C、E 按既定顺序有可追溯的集成记录；AionUi/AionCore 版本组合可复现；所有全局门禁通过；未外置的运行时职责仍留在核心，产品策略没有继续扩散到会话主流程文件中。

   ```python
            36: '036_backfill_formal_team_leader_team_id', 37: '037_enable_grok_build_team'}
   db = sqlite3.connect('<数据目录>/aionui-backend.db')
   for old, new in files.items():
       digest = hashlib.sha384(open(f'crates/aionui-db/migrations/{names[new]}.sql', 'rb').read()).digest()
       db.execute('UPDATE _sqlx_migrations SET version=?, checksum=? WHERE version=?', (new, digest, old))
   db.commit()
   ```
   影响面为内部开发机（该 bundle 未对外发布），方案：重编号 commit 落地后群内公告 + 附修复脚本。**若 local-bundle 已流出给真实用户，则需应用层 repair 逻辑，方案另议。**
2. **push 顺序**：029/030 一旦推送到 origin 任何分支并被 CI 以该 ref 为 base 检查，重编号会触发 immutability guard 的 DMR 规则。**重编号必须先于任何推送。**（当前 01d0fe88/b4ad0d1e 均未推送 ✅）
3. **窗口合并后测试基线漂移**：`run_migrations_through(34)` 在合并上游后会连带应用上游 029–032（含 030 user_scope 的 users 重建）；现有 INSERT 语句列均存在于新 schema，预判兼容，但合并后必须重跑 4 个迁移测试确认。

### C.2 执行顺序、命令与强制暂停点

1. **开窗与冻结（停机窗口开始）**

   - 停止全部使用目标数据库或 bundled binary 的 AionUi/AionCore 进程；记录操作者、开始时间、UI/Core HEAD、`git status --short`。
   - 创建仅作回退锚点的 refs：`git branch backup/window-C-ui-<timestamp> HEAD`，在 AionCore 亦创建对应 ref；创建两个独立 worktree。禁止在现有集成 worktree 合并。
   - 对每个候选 DB：先复制数据库及 `-wal`/`-shm`（如存在），再运行 `PRAGMA integrity_check;`、导出 `_sqlx_migrations(version, hex(checksum), description, success)`。

   **暂停点 C0：** 任一工作树不干净、数据库不是明确的开发副本、无法完整备份 WAL/SHM、或 bundle 仍在运行，立即停止；不得继续。

2. **仅 fetch 与目标审查（仍不合并）**

   ```bash
   git -C <AionUi> fetch upstream --tags --prune
   git -C <AionCore> fetch upstream --tags --prune
   git -C <AionUi> show v2.1.44:packages/desktop/package.json
   git -C <AionCore> show v0.1.55:crates/aionui-db/migrations/033_team_capability_criteria.sql
   git -C <AionCore> merge-base --is-ancestor <725-commit> v0.1.55
   git -C <AionCore> diff --name-status v0.1.55..upstream/main -- crates/aionui-db/migrations crates/aionui-ai-agent/src/registry.rs
   ```

   - 记录 #725 的确切 SHA、033 SQL 内容、`v0.1.55` 是否已包含它，以及目标 migration 最大号 `M`。
   - 只审查 `033_team_capability_criteria` 对 `team_capable_override`、Grok `mcp_capabilities` 和本地 037 的语义影响；不要先 cherry-pick。

   **暂停点 C1：** 若 #725/033 不是候选 v0.1.55 的祖先，或 AionUi tag 的 aioncore pin 不为 v0.1.55，先由负责人选择“调整成有正式配对的 tag”或“单独批准最小 backport”；禁止隐式吸收 upstream/main。

### C.3 失败回滚与窗口结束条件

- **Git 失败：** 丢弃窗口专用 worktree/分支，保留 `backup/window-C-*` refs；不对原集成分支使用 `reset --hard`。
- **DB 失败：** 停止新 binary，恢复完整 DB + WAL/SHM 备份；保留失败时的 migration 表与日志，不在原库反复试错。
- **bundle 失败：** 保持旧 v0.1.51 local-bundle 不变，仅归档新构建目录和 manifest；不得覆盖其文件作为回滚手段。
- **窗口可收口条件：** C0–C5 全部解除；033/#725 与本地 037 的取舍有审查记录；最终 migration 号/SQL SHA-384/存量库处理可复现；AionUi/Core/bundle 三者有同一份兼容矩阵记录。
