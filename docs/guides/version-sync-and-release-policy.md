# 版本同步与发布规范

本文档定义 AionUi / AionCore 后续的版本同步、分支职责与发版规则。后续所有更新优先按本文档执行。

## 目标

- `main` 仅作为上游同步基线
- `release/*` 作为最终交付与发版分支
- `feature/*` 只服务于对应目标线，不再混用
- 版本号、tag、发布资产保持一致

## 分支职责

### `main`

用途：同步上游代码。

规则：

- 只合并上游同步、必要的兼容修复
- 不长期承载品牌、发布、打包、发行改动
- 目标是尽量接近 `upstream/main`

### `release/<product>-vX.Y.x`

用途：最终发布线。

规则：

- 所有面向用户交付的改动最终进入这里
- 品牌、打包、发布、自动更新、兼容修复都归入这里
- 只有这里的稳定提交允许打 tag 和发版

### `feature/*`

规则：

- 从 `main` 切出：表示上游同步/通用修复
- 从 `release/*` 切出：表示产品交付/发布修复
- 功能完成后回到对应父线，不跨线乱合

## 版本与 tag

- 仅在 `release/*` 上打正式 tag
- tag 必须对应已验证可构建、可发布的提交
- 建议使用带补充分支标识的语义版本，例如：
  - `v2.1.2-pounding.1`
  - `v0.1.11-pounding.1`

## 同步流程

1. 先更新 `upstream/main`
2. 将 `main` 对齐到最新上游
3. 从 `release/*` 建立同步分支
4. 将 `main` 合入同步分支
5. 解决冲突并验证构建
6. 合回 `release/*`
7. 在 `release/*` 上创建 tag

## 工作流约定

- `main`：只做上游同步和通用修复
- `feature/*`：承载验证中的改动，验证通过后合入 `release/*`
- `release/*`：唯一允许产出正式客户端、自动更新和 tag 的分支

## 提交流程

- 任何准备进入 `release/*` 的改动，必须先完成本地验证
- 只允许通过 review 后的整合提交进入 release
- 不要直接把未验证的 feature 分支推到 release 或 tag

## 当前版本基线

- AionUi 上游基线：`v2.1.2`
- AionCore 上游基线：`v0.1.11`

后续若上游升级，先更新 `main`，再按本文档流程推进 `release/*`。
